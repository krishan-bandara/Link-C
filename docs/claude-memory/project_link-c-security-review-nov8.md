Owner asked (2026-11-08) whether Claude could "hack" the live app. Declined to send any attack traffic to the deployed site (https://link-c.innoforge.dpdns.org); did a passive header/redirect check instead (CSP, HSTS, admin redirect, 401 on no-auth API call all correct) plus `npm audit` (0 vulnerabilities). Owner then asked for 30 parallel agents; ran 30 read-only adversarial review angles (static code + live DB config via Supabase MCP, no live HTTP to the server) covering IDOR, auth/JWT, rate limits, upload content, SSRF, XSS/CSP, SQL injection, CSRF, secrets exposure, CORS, admin privilege escalation, snap tokens, SMS cost abuse, realtime auth, push hijack, location privacy, deleted-message recovery, invite brute force, password reset, timing attacks, zod validation, dependency/deploy secrets, session fixation, encryption key exposure (a few topics run twice for cross-confirmation).

**Fixed and committed (tsc clean, 38 files / 355 tests pass, next build OK):**
1. **SMS cost abuse (real, most serious):** a member could spam `POST /api/presence` every ~31s to repeatedly reset their own chat's `sms_chat_state` (the heartbeat's "came back online" branch deleted it unconditionally) and trigger 100+ SMS/hour, burning the shared daily pool (default 75) in under an hour. Fixed: `heartbeatResetAllowed()` in src/lib/sms.ts requires a 5-minute cooldown (derived from existing sms_chat_state timestamps, no new column) before a heartbeat can reset the state; `sendSms()` itself now enforces the shared daily/monthly cap for EVERY kind of SMS (alert/test/verify), not just 'alert', closing a second bypass where phone verification and test sends didn't count against the pool.
2. **Deleted message offline leak:** "delete for everyone" (added earlier the same session) was defeated by the offline cache: `sanitizeMessage` only blanked media bodies, not deleted ones, and `offline.js`'s read-only fallback page never checked `deleted_at`. Fixed in both places; text now shows "This message was deleted" there too.
3. **Snap GET CSRF hardening (low real risk, confirmed by 3 agents independently):** `GET /api/media/[id]/stream` burns a view-once image after the per-viewer signed token check; GET requests skip this app's Origin/CSRF check by design. Added a `Sec-Fetch-Site: cross-site` reject as defense-in-depth so a future weakening of the token check can't reopen a CSRF hole. Not exploitable today (token is unforgeable and viewer-bound).
4. **Video upload size/duration cap:** videos had no check mirroring the photo 4096px cap; added `videoLimitProblem()` (4096px longer side, 30 min max) via the existing ffprobe call, before ffmpeg runs.
5. **Invite token length cap:** `/api/invite/check?token=` had no length limit unlike `/api/invite/accept`'s 5000-char zod cap; added the same cap.

**Left for the owner (not code-fixable here, or a design decision):**
- **Access-token TTL still not applied (open item since earlier sessions, now confirmed sharper):** revoking a device (Settings > Devices) or the 1-minute idle logout only deletes the cookie / `auth.sessions` row client-side triggers, but nothing in RLS (`is_active_user()`) checks the JWT's `session_id` against `auth.sessions`, so the old access token keeps working until it naturally expires — likely 1 hour today, not the 300s the owner was already told to set in the Supabase dashboard (Auth settings, cannot be done via SQL/migration). Fixing this properly (making `is_active_user()` check `session_id`) is a bigger RLS change the owner should approve separately.
- **Login lockout DoS (known tradeoff, unchanged):** the 5-wrong-tries/15-min lock is keyed only on email, so anyone who knows a member's email can keep them locked out indefinitely; fixing needs an IP+email combined key which weakens brute-force protection the other way — owner must choose.
- **Location stale coordinates:** a stopped/expired share's last coordinates stay selectable directly from Supabase for up to ~20s until the worker's housekeeping sweep clears them (bounded, low severity, not fixed).
- Minor hygiene notes from the review, not fixed: `.next/standalone/.env` is a stale local leftover (gitignored, never reaches the Docker image, owner should just delete the local `.next/` folder); a timing-unsafe plaintext compare in the sign-up claim trigger (sign-up is OFF, very low risk); push-subscription-ownership TOCTOU race (needs already knowing another user's secret push endpoint, impractical).

Everything else reviewed came back clean: IDOR, SQL injection, XSS, SSRF, CORS, realtime channel RLS, push subscription ownership, admin privilege escalation, encryption key wrapping (MASTER_KEY/SIGNING_KEY never reach the client, nonces never reused), input validation coverage, and dependency/CI/secret-in-git-history checks.
