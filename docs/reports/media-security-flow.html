What happens to a photo in Link-C

From the moment someone taps send, to who can open it, and what happens to a normal photo versus a view-once snap. Checked against the real code on 2026-10-24.

1Sending: the upload pipeline

Every file goes through the same seven steps. Nothing is stored until it passes all the checks.

Phone shrinks it

Photos are reduced to 2048 px before sending. Limits: photo 10 MB, video 300 MB, voice note 25 MB.

On the phone

Logged in + in this chat

The server checks the member is signed in, is part of the conversation, and is under the rate limit (30 uploads a minute).

Gate

8 MB pieces over HTTPS

Sent through the Cloudflare tunnel (no open ports on your server). Each piece is encrypted again with a temporary key while it waits.

In transit

Real type check

The server reads the first bytes of the file. A .exe renamed to .jpg is rejected. The declared type must match the real one.

Gate

Clean and re-encode

Photos are rebuilt with sharp, videos and voice notes re-muxed with ffmpeg. This removes GPS, camera info and hidden data, and breaks image-bomb files.

Gate

Encrypt with its own key

AES-256-GCM, a fresh random key per file. That key is locked with your master key and saved in the database.

Encryption

Store under a random name

Normal: private Backblaze B2 bucket. Snaps: only the server disk. The temporary pieces are deleted.

2Viewing: who can open it?

There is no public link to any photo. Every view goes through the app, which asks the same questions each time.

Can see itThe sender and the other person in that one chat.
Cannot see itOther members of Link-C, anyone with the file's address, anyone not logged in, search engines.
What the bucket holdsOnly scrambled bytes with random names. Without the key from the database it is unreadable.

The server owner (you) holds the master key, so this is server-side encryption, not end-to-end. That was a deliberate choice.

3Normal photo vs view-once snap

Same pipeline up to storage. After that the two behave very differently.

Normal photo

stays in the chat
  • Stored encrypted in the private B2 bucket
  • Both people can open it again and again
  • The browser may keep a private copy for up to a day
  • The receiver can download it (the download button is allowed)
  • "Delete for me" hides it for that person only
  • "Delete for everyone" removes the file and its key for both
  • Backed up with normal data

View-once or timed snap

disappears
  • Stored on the server disk only. Never on B2, never in backups
  • The sender cannot open their own snap
  • Opening it is a one-time, atomic claim. Two phones cannot both win
  • Download is blocked for snaps
  • Image: the server deletes it right after the first send, even if the viewer's connection drops
  • Video: playable for up to 10 minutes after opening, then deleted
  • Never opened: deleted after 24 hours
  • A screenshot warning is sent to the sender (best effort only)

4Life of a snap, step by step

Sender sends the snapChecked, cleaned, encrypted, stored on the server disk. Expiry set to 24 hours.
Receiver taps to openThe server flips "viewed" from empty to now, in one step. A one-time pass (token) is issued: 30 seconds for a photo, 10 minutes for a video.
The pass is checked on every requestIt only works for that file and that person. The reply is never cached (no-store).
The photo is streamed, then burnedThe server marks it deleted before sending, then removes the file and the key when the last byte goes out.
GoneOpening again gives "This snap is no longer available" (410 or 409).
If nobody opens it
After 24 hours a background worker deletes the file and its key.
If something goes wrong halfway
A failed upload is rolled back: the stored file and the message are removed, temporary pieces are cleaned up.
Abandoned uploads are cleared after a short time, so they cannot fill the disk.
Screenshot report
If the viewer's phone reports a screenshot, a system line appears in the chat once per view. Browsers cannot truly block or detect all screenshots.

5Honest limits

  • Screenshots and cameras: anyone who can see a photo can screenshot it, or photograph the screen with another phone. A normal photo can also be downloaded. No chat app can fully stop this.
  • Server-side encryption: whoever controls the server and the master key can technically decrypt files. Keep MASTER_KEY private and backed up.
  • Stolen account: someone with a member's password and phone sees what that member sees. Login locks for 15 minutes after 5 wrong tries, and the app logs out after 1 idle minute.
  • Review status: an internal security review found 0 critical and 1 high issue (a crash from a huge crafted image, fixed). A human penetration test is still recommended.
