Link-C: full architecture

Private, invite-only, secure chat web app (PWA) for 1 to under 50 people. State as built on 2026-10-19. Personal project, separate from any Softlogic system.

1. Overview

What it is

  • WhatsApp-style chat: text, emoji, reactions, stickers, photos, videos, view-once snaps, voice/video calls, consent-based location sharing.
  • Invite-only: the owner invites people; public sign-up is disabled.
  • Works as an installable web app (PWA) on PC, Android and iPhone.
  • Night-sky glass design (cyan to violet), dark and light modes, accent colours, wallpapers.

Key decisions

  • Login: email + password. No emailed links or codes. One-time invite link, person picks name + strong password.
  • Server-side encryption (not end-to-end): files encrypted per file with AES-256-GCM, wrapped by a master key.
  • Database: owner's personal free Supabase cloud project (Mumbai), not self-hosted.
  • Hosting: Docker Compose on a Linux VM, published to the internet only through a Cloudflare Tunnel (no inbound ports).
  • Auto sign-out after 1 minute of inactivity.

6. Authentication and sessions

  1. Invite. Owner enters email, name, optional phone in Admin > Members. The server stores the invite and returns a one-time link (24 h, only its hash is stored).
  2. Accept. The person opens /invite/<token>, picks a name and a strong password (live strength meter). The server claims the token atomically, arms a one-time claim secret on the invite, and creates the Supabase user with that secret. The database trigger checks and wipes it.
  3. Sign in. POST /api/auth/login: per-IP limit (20 per 10 min), atomic per-email lockout (5 wrong tries lock 15 min), generic error for wrong password, unknown email and disabled account alike.
  4. Session. Supabase cookies plus an HMAC activity cookie lc-act. Middleware refreshes the session and rejects sessions idle for more than 90 s.
  5. Idle logout. IdleGuard warns at 45 s and signs out at 60 s; an active call, upload or location share keeps the session alive.
  6. Disable / reset. Owner disables a login (auth ban, sessions revoked, flag set; RLS also stops direct access immediately) or issues a reset link. Password change keeps your own session and revokes the others.
  7. Refresh or close. The browser confirmation box appears; confirming ends the session so the next load starts at login.

7. Messaging and realtime

  • Text messages are inserted by the browser straight into Postgres under RLS (participants only, type text, rate-limited by the database).
  • Stickers, media and snaps go through API routes that verify participation and use the service key.
  • Realtime: Postgres changes on messages update the chat and the list; private broadcast channels conv:<id> carry typing and online presence. The client calls realtime.setAuth() before subscribing; one shared channel per conversation.
  • Ticks: sent, delivered, read (blue) via mark_delivered/mark_read.
  • Clear chat hides history for one person only (policy on messages compares with conversation_clears).
  • Sounds: short Web Audio tones for receive, in-chat and send; on/off and volume stored per device.

8. Media, stickers and snaps

Normal photos and videos

  1. Client sends 8 MiB chunks (resumable) to /api/uploads.
  2. Server assembles, checks real file type, strips metadata, makes a thumbnail.
  3. Each file is encrypted with its own AES-256-GCM key (1 MiB segments, range requests supported); the key is wrapped by the master key.
  4. Ciphertext goes to Backblaze B2; reads are decrypted on the fly through a local encrypted cache.

Limits (admin-editable): photo 10 MB, video 300 MB, temp cap 3 GB.

Snaps (view once / timed)

  • Stored only on the VM disk, encrypted, never in B2 or backups.
  • Deleted after the first view, or after 24 hours if unopened.
  • Viewer blocks save and context menu; screenshot detection is best effort only.

Stickers and profile images

  • 96 official Microsoft Fluent Emoji stickers (MIT licence, credited in-app) in six packs, plus personal sticker packs.
  • Avatars and wallpapers are encrypted assets served through access-checked routes.

9. Alerts when someone is away

Push notifications (free, primary)

  1. Person turns on Phone notifications in Settings once (iPhone: Add to Home Screen first) and taps Allow.
  2. The browser creates a push address; /api/push/subscribe stores it (only real push-service hosts are accepted).
  3. Worker finds people with unread messages who have been away longer than the admin-set delay and have a subscription.
  4. It sends one generic push (title and message from Admin > Push) per away period; dead subscriptions are removed.
  5. Service worker shows the notification; tapping opens the app.

SMS (optional backup)

  • Generic HTTP gateway adapter: URL, method, format, templates and credentials are set in Admin > SMS. Placeholders: {to} {toDigits} {text} {sender} {apiKey} {apiSecret} {basicAuth}.
  • One text per offline period, daily and monthly caps, quiet hours, per-member opt-in and verified phone.
  • Credentials are encrypted at rest and write-only in the UI; the gateway URL must be public https (SSRF guard).

13. Deployment

  1. Supabase dashboard: sign-up OFF, Site URL = app URL, Email provider ON, Realtime public access OFF, optional short token lifetime (about 300 s).
  2. Cloudflare: route link-c.innoforge.dpdns.org to http://127.0.0.1:3005 on the existing tunnel; Access on /admin*. Never rotate the shared tunnel token.
  3. Server: copy the project (without node_modules, .next, qa, .env.local), create .env (chmod 600), mkdir -p data && chown 1000:1000 data.
  4. docker compose build && docker compose up -d.
  5. Owner first login via scripts/owner-set-password-link.mjs; invite members from Admin.

Environment variables (names only): NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY, SUPABASE_SECRET_KEY, MASTER_KEY, SIGNING_KEY, APP_URL, B2_*, DATA_DIR, LIVEKIT_*, VAPID_PUBLIC_KEY, VAPID_PRIVATE_KEY, VAPID_SUBJECT, TZ.

Server size: 1 vCPU, 1 GB RAM, about 25 GB disk is comfortable (app uses roughly 150 to 200 MB, worker about 35 MB). A region near Mumbai keeps database round trips short.

14. Operations

  • Backups: free Supabase has no restorable backups; run a nightly encrypted pg_dump and keep a copy of MASTER_KEY offline (losing it makes stored media unreadable).
  • Pausing: free Supabase pauses after 7 idle days.
  • Monitoring: worker logs a warning when the disk passes 80%; admin dashboard shows storage and failures.
  • Secret rotation: rotate the Supabase secret key and the Backblaze key after go-live. Changing the VAPID pair makes every phone subscribe again.
  • Emergency access: scripts/owner-login-link.mjs and owner-set-password-link.mjs (need the service key).

15. Known limits and risks

  • Encryption is server-side: whoever controls the server and MASTER_KEY can read media.
  • Snaps can be photographed or screen-recorded; screenshot alerts are best effort.
  • Push needs the https address; iPhone needs the app added to the Home Screen; people who never allowed notifications get nothing.
  • Carriers may filter SMS; the free gateway tier is limited.
  • Page loads are slower on slow phones because the database is remote; abandoned uploads count for up to an hour.
  • A person who knows an email can lock that account for 15 minutes by guessing; the owner can unlock with a reset link.
  • Rate limits are in memory per process (reset on restart; not shared across replicas).

18. Testing summary

  • 90 unit tests (crypto, SSRF guards, password, idle, login guard, assets, credits, emoji, push allow-list, worker helpers) plus an RLS SQL test.
  • About ten parallel QA agents covered: design and responsive layout, full first-time journeys, chat features, admin, security and APIs, accessibility, performance and resilience, regression of late changes.
  • Sign-up lock-down verified: public sign-up and forged claims are refused, real invites still work.
  • All throwaway data removed afterwards; only the real owner, one real member and the six official sticker packs remain.
