Verdict

  • No critical issues. One high issue: a small image could crash the app (memory exhaustion). It was reproduced live and is fixed (images over 40 megapixels are refused).
  • Every medium finding in the code that could be fixed in code was fixed: the login redirect, cross-site request checks, the long-lived session cookie, the stale base image and the vulnerable build dependency.
  • Still open and needing your action in dashboards: Supabase token lifetime (about 300 s), leaked-password protection, password rules and rate limits at Supabase (the app lockout can be bypassed by calling Supabase directly), and the server steps in DEPLOY.md.
  • Still open in code, recommended before many users: a storage quota for snaps and media (the setting exists but is not enforced).
  • No injection or script execution was possible in any text field tested; no way to read another person's data was found by the code reviewers or the database review; encryption, tokens, invite flow and the sign-up lock held up.
What was NOT tested live (be aware): several live attack tests were stopped by an automated safety check or ended without results and were NOT run: login brute-force and lockout bypass, the full authorization (IDOR) suite, location and call-token tests, realtime channel attacks, media and snap fetch attacks, and invite-token race tests. For those areas the code reviews and the earlier QA rounds (which did test lockout, disabled accounts, database access by members, snap access and token flows) are the evidence. A hands-on penetration test by a human is still recommended before wide use.

Live attack test: upload abuse
 src/lib/upload-process.ts (sharp(rawPath, { animated }) in step 3, approx. lines 98-112); POST /api/uploads/[id]/complete Chat images are re-encoded with sharp using the default input pixel limit (268 MP) and animated:true for WebP/GIF, with no frame or total-pixel budget. A small file that declares 16000x16000 pixels decodes into hundreds of MB to over 1 GiB of RAM. The app container has a 1 GiB memory limit, so the Node process is killed and restarted (docker RestartCount rose 0 to 2 over two reproductions). All users get dropped connections during the restart, and the in-flight upload session stays stuck in 'processing'. A 16000x16000 JPEG (1.5 MB) pushed the container to 963-1023 MiB but survived; a 16000x16000 WebP (455 KB) killed it both times. The same cause means a pixel bomb at 12000x12000 (140 KB PNG, 144 MP) is accepted, stored and served to the recipient, whose phone or browser must decode a 144 MP bitmap (about 576 MB) which likely crashes the recipient's tab. Avatar, wallpaper and sticker paths are fine because they set limitInputPixels to 40 MP.
Attack: 1) Sign in as any member who is in a conversation. 2) Make a solid 16000x16000 WebP (node: sharp({create:{width:16000,height:16000,channels:3,background:'#1464c8'}}).webp({quality:50}).toFile('x.webp') gives 455 KB). 3) POST /api/uploads {conversationId, mime:'image/webp', size:455242, mode:'normal'}; PUT /api/uploads/<id>/chunk?i=0 with the file; POST /api/uploads/<id>/complete. 4) 'docker stats linkc-app-1' hits 1024MiB and the container restarts; the next request fails with 'other side closed'. Authentication, sessions and API routes (code review)
